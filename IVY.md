# Ivy SCA examples

These projects exercise native Ivy resolution and Java call-site analysis. They
contain intentionally vulnerable versions; they are scan fixtures.

| Project | What to verify |
| --- | --- |
| `ivy-basic` | Direct `commons-collections:commons-collections:3.2.1`, with a Java caller. |
| `ivy-transitive` | Direct `commons-beanutils:commons-beanutils:1.9.2` brings in `commons-collections:commons-collections:3.2.1` and `commons-logging:commons-logging:1.1.1`. |
| `ivy-private-layout` | A repository-local Ivy descriptor for `com.northbeam:template-client:1.0` brings in `org.apache.commons:commons-text:1.9` and then `org.apache.commons:commons-lang3:3.11`. Settings includes and a properties file supply the private resolver and version. |

Each project has an `expected-graph.json` listing exact packages, directness and
adjacent dependency edges. `ivy.xml` should be the finding/inventory manifest;
packages use the Maven ecosystem and `organisation:module` names. Transitive
findings should have a path starting at the declared direct dependency, and
SBOMs should retain the same edges. No Maven, Gradle or sbt manifest is needed.
The private layout contains metadata and library source, not a published JAR;
SCA resolution reads descriptors without building or downloading artifacts.

All examples explicitly map the application's `runtime` configuration to the
dependency's `default` configuration. Ivy otherwise may select dependency test
configurations too. The scanner resolves every application configuration.

For a remote private layout, publish the descriptors under the same paths as
`ivy-private-layout/repository`, and adapt `ivysettings.remote.example.xml` into
the project's `ivysettings.xml`. Add a Maven package-registry connection in
ZeroPath pointing at the HTTPS repository root, with its Basic or Bearer
credentials. Keep credentials out of project settings and URLs. Authentication
is limited to that repository's origin and path; redirects to other locations
do not receive it.

An air-gapped installation needs the normal local OSV snapshot plus mirrored
package metadata. `sca.registries.maven` supplies Maven Central dependencies,
including those fetched by Ivy. A remote Ivy layout additionally uses:

```yaml
sca:
  registries:
    maven: https://artifactory.internal/maven-central
  sandbox:
    ivyMirrors:
      - source: https://packages.example.com/ivy
        mirror: https://artifactory.internal/ivy
        probe: com.northbeam/template-client/1.0/ivy-1.0.xml
```

The probe is an existing descriptor path relative to both roots. Installation
preflight must be able to read it anonymously through the deployment's outbound
guard and CA trust. Per-organization credentials are exercised by the subsequent
scan. A failed mirror does not fall back to its original source. For the
committed filesystem example only the Maven mirror is needed.

Use the next-generation SCA engine and an Ivy-capable resolver image. Ant
targets, custom resolver plugins, SSH/SFTP repositories, embedded credentials,
and properties computed by a build are unsupported; resolution failures must
show a coverage warning. Ivy dependency upgrade patches are not generated by
the Maven `pom.xml` updater.
